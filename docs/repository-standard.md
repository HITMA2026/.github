# HITMA 仓库建设与协作规范

- 版本：1.0
- 更新日期：2026-11-08
- 适用范围：HITMA2026 组织内的软件、硬件、教程与资料仓库。

本规范的目标是让成员接手仓库时，能够知道项目做什么、怎么使用、验证到了什么程度，以及遇到问题找谁。

“必须”表示新建仓库的最低要求；“建议”表示按项目需要采用。已有仓库在后续维护中逐步补齐。项目存在不同需求时，在 README 中说明原因与替代做法，由项目维护者记录并执行。

## 1. 仓库划分与命名

- 一个仓库必须围绕一个明确、可维护的项目。紧密关联的软件、硬件和说明可共同维护；无关项目分别建仓库。
- 新仓库名称使用小写英文、数字和连字符，优先表达用途，例如 `uav-flight-control`、`vision-target-detection`、`embedded-learning`。
- 确实按届次独立维护的项目可使用 `cuadc-2026` 一类名称。同一项目的日常改进使用提交、分支和标签管理。
- GitHub 有固定用途的名称，如 `.github` 和 `HITMA2026.github.io`，按平台要求保留；已有名称不因本规范强制变更。
- 仓库必须填写一句话简介。建议补充技术方向等 Topics，方便成员查找。

## 2. README 与项目责任

每个仓库必须提供首页 README，至少说明：

| 信息 | 要回答的问题 |
| --- | --- |
| 项目用途 | 解决什么问题，适用哪些设备、任务或学习场景？ |
| 负责人 | 谁负责维护，如何通过 GitHub 联系？ |
| 项目状态 | 开发中、维护中或已归档？最近可用的版本是什么？ |
| 使用入口 | 从哪里安装、构建、启动，或者查看图纸和学习资料？ |
| 目录说明 | 主要内容分别存放在哪里？ |
| 验证状态 | 做过哪些检查或测试，结果对应哪个提交？ |
| 已知问题 | 有哪些限制、未完成内容和后续任务？ |
| 来源与许可 | 哪些内容来自第三方，使用条件是什么？ |

可以从 [README 范本](../templates/README-template.md) 开始，按项目类型删去不适用项。文档仓库不必填写软件构建步骤，但必须说明阅读顺序、适用对象和资料组织方式。

## 3. 目录与文件组织

项目必须将不同用途的内容合理分开，并在 README 解释主要目录。目录按实际需要建立，不要求创建空目录。

软件项目可参考：

```text
project/
├── README.md
├── src/        # 源码
├── config/     # 可复用配置与示例
├── docs/       # 设计、部署、接口与验证说明
├── scripts/    # 安装、构建、启动等辅助脚本
├── tests/      # 有实际验证价值的测试
└── .gitignore  # 构建产物与本地文件的排除规则
```

已有框架或工具链规定结构时，沿用其结构。例如 ROS 工作空间保留包结构，嵌入式工程保留工具链所需文件。

硬件项目建议区分 `hardware/`、`firmware/`、`mechanical/` 和 `docs/`；教程与资料项目可采用章节目录、`examples/`、`assets/` 等结构。

源码及脚本路径建议使用清楚、稳定的英文名称。中文文档和章节名可以保留；避免在构建路径中使用含糊名称、无意义编号和不必要的空格。

## 4. 环境、依赖与使用步骤

### 软件项目

必须记录实际使用的操作系统、工具链、框架及关键依赖版本，并给出：

1. 获取项目和必要子模块、资源的方式。
2. 安装依赖的方法与依赖清单；工具支持且项目需要时提交锁文件。
3. 构建命令、执行目录和前置条件。
4. 启动方法、使用的配置，以及如何停止程序。
5. 检查运行是否正确的方法和预期结果。

文档中的示例值必须与真实设备参数区分。配置发生变化时同步更新说明，必要时提供不含本地凭据的配置范本。

推荐提供可重复执行的构建或检查脚本。需要专用设备、付费软件、指定网络或外部资源时，写明条件与获取途径。无法完整复现的部分应明确说明原因。

### 硬件项目

必须说明主要硬件型号、设计软件及版本、接口或接线、供电条件，以及图纸、BOM 和固件之间的对应关系。需修改设计时保留可编辑源文件；生产或装配所需导出文件注明对应版本。

### 教程与资料项目

必须说明读者需要的基础、学习或阅读顺序、示例运行条件和引用来源。示例代码与正文应保持一致。

## 5. Git、分支与协作

- 默认分支承载当前主要维护内容。新仓库建议使用 `main`；已有仓库可保留默认分支名称。
- 日常功能开发使用工作分支，例如 `feat/mission-planner`、`fix/serial-timeout`、`docs/setup`。
- 多人维护的功能修改通过 PR 合入。一次 PR 围绕一个明确目标，说明改了什么、为什么改、如何验证。
- 涉及飞控逻辑、硬件接口、通信协议及关键参数的修改，合入前应由另一名相关成员审查。
- 单人项目或小范围文档修订可由维护者直接提交，并保留清楚的修改说明与检查记录。
- 提交信息写明实际改动。建议使用 `feat:`、`fix:`、`docs:` 等前缀，正文可使用中文。
- 共享分支避免改写已有历史；项目负责人按需配置分支保护、审查要求和 `CODEOWNERS`。

不通过复制完整工程到“最终版”“最终版2”“备份最新版”等目录管理版本。用于对照的实验或历史资料可以保留，但应说明用途、来源和与当前项目的关系。

## 6. 验证与结果记录

修改后必须完成与改动相匹配的检查；无法完成的检查应写明原因和待验证内容。

| 验证范围 | 应保留的信息 |
| --- | --- |
| 文档与配置检查 | 链接、命令、路径、配置语法是否正确 |
| 构建与自动检查 | 命令、环境、结果，失败时的关键信息 |
| 仿真 | 仿真平台、场景、参数、判断标准与结果 |
| 台架 | 硬件组合、接线、固件、输入条件与结果 |
| 实机 | 设备、软件与硬件版本、配置、测试条件、结果和异常 |

各类验证独立描述。编译成功不代表仿真、台架或实机通过；只验证了某个模块时，不写成整机验证通过。

对飞控、视觉和嵌入式项目，结果必须能对应到 Git 提交或标签，并注明配套固件、硬件、配置文件和必要的标定版本。未验证的状态如实填写“未验证”。

关键阶段或交接前建议保存一份[验证记录](../templates/validation-record-template.md)。记录可使用 Markdown、Issue 或其他团队可访问的方式；大体积数据通过链接关联。

适合自动化的构建、格式检查、测试或文档检查可接入 CI。需要实际设备的验证单独记录，CI 结果只代表其覆盖的检查范围。

## 7. 提交内容与大文件

必须提交复现项目所需的源码、可维护配置、构建描述、依赖清单及使用说明。项目自身通过 `.gitignore` 排除生成的构建目录、缓存、临时文件和本地凭据。

- 模型权重、数据集、视频、飞行日志和大型设计文件按项目需要使用 Release 附件、Git LFS 或团队可访问的存储。
- 外部资源必须保留获取位置、版本或文件标识、使用说明；需要核对文件完整性时记录校验值。
- 需要随源码维护的二进制文件可以保留，但应说明用途与来源。
- 不提交密钥、口令等凭据；公开日志和截图前移除个人信息及不宜公开的数据。
- 不以多个压缩包替代可维护的项目源码；历史归档包应单独说明。

## 8. 发布、归档与交接

阶段成果建议使用标签标记，例如软件 `v1.0.0` 或硬件 `hw-r1`，具体规则由项目在 README 中说明。正式发布时记录主要变化、适用环境、已知问题和验证范围。

交接或停止维护前必须更新：

- 负责人及维护状态。
- 最近可用的提交或标签和复现方法。
- 配套硬件、固件、配置与资源的获取方式。
- 已知问题、未完成任务及必要的设计说明。

资料仍可参考但不再维护的项目，在 README 中标记“已归档”。维护者按实际需要启用 GitHub 的归档功能。

## 9. 第三方来源与公开范围

引用代码、模型、图纸、图片或资料时，必须注明来源并保留原有许可声明。修改第三方内容时说明改动范围。

公开前由负责人确认项目内容可以公开，并在仓库内明确许可证及适用范围。代码、硬件和文档需要不同许可时，分别说明。暂未确定的许可状态应如实记录，不默认授予使用权。

## 10. 新建仓库检查清单

- [ ] 仓库名称和简介表达清楚。
- [ ] README 写明用途、负责人、维护状态和目录。
- [ ] 环境、依赖和使用步骤适合项目类型。
- [ ] 配置范本、必要资源及获取方式齐全。
- [ ] 验证范围、对应版本和已知问题如实记录。
- [ ] 无无关缓存、本地凭据和工程版本副本。
- [ ] 第三方来源、公开范围与许可状态清楚。
